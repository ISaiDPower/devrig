# DevRig design

> **Status:** draft for discussion. Everything here can change until the first release.

## Goals

- **Native.** Real binaries on the host. No containers, no virtual machines.
- **Per project and reproducible.** A project describes its environment in `devrig.toml`. Anyone who clones it and runs `rig up` gets the same versions.
- **Side by side.** Several versions of PHP, Node.js and the rest can be installed at once.
- **One engine, two front ends.** The `rig` CLI and the DevRig desktop app are thin clients over the same core.
- **Windows first.** macOS and Linux follow, so nothing in the core may assume Windows.
- **Minimal elevation.** Admin rights only for a few narrow, explicit operations.

### Non-goals (for now)

- Production deployments.
- Containers or remote environments.
- Migrating database data between major versions.

## Concepts

| Concept | Meaning |
| --- | --- |
| **Package** | Anything DevRig can install, described by a recipe. Runtimes (PHP, Node.js), services (Nginx, Mailpit, MySQL) and tools (Composer, pnpm) are all packages. |
| **Release** | One exact version of a package, for example `php 8.3.14`. Releases live side by side. |
| **Extension** | An add-on for a runtime, such as a PHP extension. Extensions are packages that depend on a runtime release. |
| **Project** | A directory with a `devrig.toml`. |
| **Site** | A project served on a local domain, for example `https://shop.test`. |
| **Agent** | The background process that supervises services and sites. |

## Directory layout

Everything DevRig owns lives under one root, overridable with `DEVRIG_HOME`:

| OS | Default root |
| --- | --- |
| Windows | `%LOCALAPPDATA%\DevRig` |
| macOS | `~/Library/Application Support/DevRig` |
| Linux | `$XDG_DATA_HOME/devrig` |

```
DevRig/
  packages/<name>/<version>/   unpacked releases, read only after install
  downloads/                   download cache, keyed by sha256
  shims/                       on PATH, resolves the right version per project
  services/<name>/<version>/   generated config and logs
  data/<name>/<major>/         service data (databases), kept across upgrades
  sites/                       generated web server config per site
  ca/                          local certificate authority
```

Data is kept apart from packages so that upgrading or removing a release never deletes a database.

## `devrig.toml`

```toml
[runtimes]
node = "22"

[runtimes.php]
version    = "8.3"
extensions = ["redis", "imagick", "xdebug"]
ini        = { memory_limit = "512M", "xdebug.mode" = "debug" }

[tools]
composer = "2"

[services]
mailpit = {}
mysql   = { version = "8.4", port = 3306 }

[site]
domain = "shop.test"
root   = "public"
https  = true
```

- **`[runtimes]` and `[tools]`** both put executables on PATH for the project. The split is only for readability.
- **Short and long forms:** every entry accepts a version string (`node = "22"`) or a table with `version` plus package specific options.
- **`[services]`** lists what the project needs running. Services are shared between projects, see [Services](#services).
- **`[site]`** serves the project on a local domain. `root` is the document root relative to the project. A site can use `proxy = "http://127.0.0.1:3000"` instead of `root`, for Node.js or Go apps.
- **Integration:** declaring `mailpit` also configures PHP's `sendmail_path` and SMTP settings to deliver to it.

### Version constraints

A constraint is a version prefix:

| Constraint | Resolves to |
| --- | --- |
| `"8"` | the highest `8.x.y` |
| `"8.3"` | the highest `8.3.y` |
| `"8.3.14"` | exactly `8.3.14` |

### `devrig.lock`

`rig up` resolves constraints to exact versions and writes them to `devrig.lock`, which is committed with the project. Later runs install exactly what the lock file says. `rig update` resolves again and rewrites it.

```toml
# Generated by rig. Do not edit.
version = 1

[packages]
php      = "8.3.14"
node     = "22.11.0"
composer = "2.8.3"
mailpit  = "1.21.5"
mysql    = "8.4.3"

[extensions.php]
redis   = "6.1.0"
imagick = "3.7.0"
xdebug  = "3.4.0"
```

The lock file pins versions only, so it works across operating systems. Integrity comes from the checksums in the recipes.

## Recipes

A recipe describes how to fetch, install and run one package. Recipes live in `recipes/` in this repository and are shipped as a single index file. Each package has two parts:

**`recipes/<name>/recipe.toml`** is written by hand and describes behaviour:

```toml
name     = "mailpit"
kind     = "service"
homepage = "https://mailpit.axllent.org"
bin      = ["mailpit"]

[service]
command = "{{.Bin}}/mailpit"
args    = [
  "--smtp", "127.0.0.1:{{.Ports.smtp}}",
  "--listen", "127.0.0.1:{{.Ports.http}}",
  "--database", "{{.Data}}/mailpit.db",
]
ports = { smtp = 1025, http = 8025 }
ready = { tcp = "smtp" }
```

**`recipes/<name>/versions.json`** is generated and lists every release with a download URL, size and sha256 per OS and architecture:

```json
{
  "1.21.5": {
    "windows/amd64": {
      "url": "https://github.com/axllent/mailpit/releases/download/v1.21.5/mailpit-windows-amd64.zip",
      "sha256": "<checksum>",
      "size": 9123456
    }
  }
}
```

### Why static version lists

Upstream projects publish releases in very different ways. For example, windows.php.net has a `releases.json`, Node.js has `dist/index.json`, Go has `go.dev/dl/?mode=json` and Mailpit uses GitHub releases. Instead of teaching `rig` all of these at runtime:

- an **updater** (Go code in this repo, run on a schedule by GitHub Actions) reads upstream, verifies what it can (checksums, PGP signatures) and opens a pull request with the new `versions.json` entries;
- **`rig` only reads data.** It stays simple, works offline from the cache and never installs a checksum it has not seen in a reviewed recipe.

A later step is signing the published index, so a compromised download host cannot change checksums.

### Delegated packages

Some ecosystems already have a good installer. Reimplementing them would be worse:

- **Rust:** `rig` installs and drives `rustup`. `rust = { version = "stable", components = ["clippy"] }` maps to rustup toolchains.
- **Python:** uses the python-build-standalone builds, the same ones `uv` uses.

## Shims and PATH

The installer adds `DevRig/shims` to the user PATH. Each shim (`php.exe`, `node.exe`, `composer.cmd` and so on) is a small binary that:

1. walks up from the current directory to find the nearest `devrig.toml`;
2. resolves the version from `devrig.lock`, falling back to the global default (`rig use -g php@8.3`);
3. starts the real executable, forwarding arguments, stdio, Ctrl+C and the exit code.

Shims work the same in cmd, PowerShell, Git Bash and IDEs, which shell hooks do not.

## Agent

`rig agent` is a per-user background process. It is not a Windows service, because services run as another account and cannot see the user's projects properly.

- **It supervises service processes:** start, stop, restart on crash, logs and readiness checks.
- **It owns the web server config:** it regenerates site config and reloads Nginx when sites change.
- **It keeps services running when the GUI is closed,** because the GUI and the CLI are only clients.
- **The API is HTTP over a named pipe on Windows** (a Unix socket elsewhere), only accessible to the current user.
- **It starts on demand** the first time `rig` or DevRig needs it, and optionally at login.

## Services

Services are machine wide, not per project, the same way Laragon and Herd work:

- **One instance per version.** If two projects need `mysql 8.4`, they share one instance. Different major versions get different ports.
- **One web server owns ports 80 and 443** and serves every site. The MVP uses Nginx. Apache will run behind it for projects that need `.htaccess`.
- **Mailpit** is a single shared instance.
- **`rig down`** stops a project's site and any service no other active project needs.

### PHP on Windows

Windows has no `php-fpm`, and `php-cgi.exe` handles one request at a time. The agent therefore runs a small pool of `php-cgi.exe` processes per PHP version, behind an Nginx `upstream`. It restarts them when they exit (`PHP_FCGI_MAX_REQUESTS`). DevRig uses non thread safe (NTS) builds everywhere.

## Sites, domains and HTTPS

- **Domains:** `.test` by default. Their hosts file entries live in a block marked as owned by DevRig. `.localhost` is offered as a zero setup option, because browsers resolve it to loopback without hosts entries (other clients may not).
- **HTTPS:** DevRig creates a local certificate authority once, trusts it in the current user's root store and issues a certificate per site.

### Elevation

On Windows, binding ports 80 and 443 needs no admin rights. Trusting a root certificate in the current user store shows a confirmation dialog but needs no admin either. That leaves one privileged operation:

- writing the DevRig block of the hosts file.

It runs as a separate elevated invocation (`rig elevated hosts-sync`, started through UAC). It does only that and validates its input.

## PHP extensions

- **Bundled extensions** (`mbstring`, `curl`, `pdo_mysql` and others) ship with PHP and only need enabling in `php.ini`.
- **External extensions** (`redis`, `imagick`, `xdebug` and others) are packages with releases per PHP minor version, NTS or TS, and architecture. On Windows these are prebuilt DLLs. On macOS and Linux they have to be built or fetched from a binary source.

Open question: reuse the metadata from [PIE](https://github.com/php/pie) instead of maintaining our own extension index.

## CLI surface (draft)

```
rig init                    create devrig.toml in the current directory
rig up                      install what is missing, start services, set up the site
rig down                    stop this project's site and unused services
rig install <pkg>@<ver>     install a release
rig uninstall <pkg>@<ver>   remove a release
rig list [--available]      show installed (or installable) releases
rig use [-g] <pkg>@<ver>    pick a version for this project or globally
rig which <command>         show which executable a shim resolves to
rig start|stop|restart      control services
rig status                  show services and sites
rig logs <service>          follow service logs
rig update [pkg]            resolve versions again and rewrite devrig.lock
rig doctor                  check PATH, shims, certificates, hosts and ports
```

## Code layout

```
cmd/rig/            CLI entry point
cmd/rig-shim/       shim binary
gui/                DevRig desktop app (Wails)
internal/cli/       commands
internal/config/    devrig.toml and devrig.lock
internal/registry/  recipes and version lists
internal/install/   download, verify, extract
internal/shim/      shim resolution
internal/agent/     agent process and its API
internal/service/   process supervision
internal/site/      web server config, hosts, certificates
recipes/            recipe definitions
tools/updater/      generates versions.json from upstream
installer/          NSIS script
```

2. **Multiple sites per project:** `[[site]]` arrays?
3. **Existing version files:** should `rig` read `.nvmrc`, `.python-version`, `rust-toolchain.toml` and `.tool-versions` when `devrig.toml` does not set a version?

5. **Index hosting and signing:** GitHub releases, GitHub Pages, or something else?
